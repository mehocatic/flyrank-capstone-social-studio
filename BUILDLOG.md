# Build log

Honest record of how this was built: where AI (Claude Code) helped, where it was wrong, what changed.

## Phase 1: Design

- **2026-10-19: design doc drafted** ([docs/DESIGN.md](docs/DESIGN.md)).
  - AI helped: drafted the data model, the publish path (claim → write-ahead attempt → send → record) and the constraint profiles from my fixed decisions (SQLite job store, Discord webhook as the real target, two mocks, templates instead of AI).
  - Checked before deciding: a throwaway script confirmed that Node 24's built-in `node:sqlite` supports `UPDATE … RETURNING` (atomic claim) and a partial unique index (one success per job). It prints an ExperimentalWarning. It still beats `better-sqlite3`, which needs a native build on the reviewer's machine.
  - Decision: when a Discord send is ambiguous, the job is parked as `unknown` (at-most-once), not retried. A webhook has no idempotency key, so retrying could post twice.

## Phase 2: Ingestion and generation

- **2026-10-19: scaffold, config and schema.** `package.json`, `tsconfig.json` (strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`), `src/config.ts`, `src/db/`, `GET /health`. Builds clean; `GET /health` and the 404 error shape verified by hand.
  - Dependencies: `express` only. `.env` is read by Node's own `process.loadEnvFile`, so no `dotenv`; SQLite is `node:sqlite`, so no native build.
  - AI got it wrong first: the initial import was `from './schema.ts'`, which TypeScript rejects for a compiled project (`.ts` imports need `allowImportingTsExtensions`, which only works with `noEmit`). Changed to `./schema.js`, the standard NodeNext style, where the source is `.ts` and the import names the emitted file.
  - My call, not the AI's default: config is validated once at boot and nothing else reads `process.env`. Proven by booting with `PLATFORMS` including `discord` and no webhook URL: it exits 1 with a message naming the fix instead of crashing later inside the worker.
  - Added a guard the design doc implies but did not state: `WORKER_LEASE_MS` must exceed `PUBLISH_TIMEOUT_MS`, else a lease can expire while a send is still in flight.
  - Node floor set to **24**, the version this was actually built and run on (24.14.0). An earlier draft claimed 22.13 from reading release notes. I removed that: a verified claim beats an assumed one, and nobody had run the code on 22.13.
- **2026-10-19: ingestion.** `POST /posts` (either `{url}` or `{markdown}`), `GET /posts/:id`, `GET /posts`. 13 cases checked by hand against a running server, including a real fetch of `https://example.com/` that extracted the title and body correctly.
  - No Markdown or HTML parser dependency. The system needs a title, plain prose and tags, so `src/posts/markdown.ts` does that with regexes. A real parser would be more correct on exotic input and more code than I can defend line by line.
  - AI got it wrong again, same root cause as the import: `node:sqlite` types every row as `Record<string, SQLOutputValue>`, so `.get(...) as PostRow` failed to compile ("neither type sufficiently overlaps"). Rather than scatter `as unknown as` casts, I added `queryOne` / `queryAll` / `execute` in `src/db/index.ts`. The unchecked cast now lives in one reviewable place, and the schema's CHECK constraints are what actually hold the union types honest.
  - Added beyond the design doc: an SSRF guard in `src/posts/fetchUrl.ts`. `POST /posts {url}` makes the server fetch an address a caller chose, so loopback, private and link-local addresses are refused. Verified with `169.254.169.254` (the cloud metadata address). The comment states the limit honestly: the check does not resolve DNS, so a hostname pointing at a private IP would still pass.
  - The URL is fetched **once**, at ingest. Generation reads only the stored row, so a variant cannot change later because the blog did. That is the brief's "stored post is the single source of truth".
- **2026-10-19: constraint profiles and validator.** `src/platforms/profiles.ts` (rules as data), `src/platforms/validate.ts`, `GET /platforms`, and 19 unit tests. `npm test` passes 19/19.
  - Tests, not just transcripts, by my call: a reviewer can rerun `npm test`, while a pasted curl transcript only shows it worked once on my machine. Same reason the idempotency and crash paths will get tests in phase 4.
  - Profiles are **data, not code**. Adding a rule to a platform is an edit to one object, and the validator needs no new branch. This is what keeps the enforcement honest when a platform's limits change.
  - The validator reports **every** broken rule, not the first. A caller fixing a variant should not have to submit five times to discover five problems.
  - A real bug the tests caught, in my own test: I asserted that `findHashtags('…/guide#setup')` returns `['#setup']` *and* that the validator ignores it, which cannot both hold. The code was right (the lookbehind refuses a `#` that follows a word character, and URLs are stripped before counting); the expectation was wrong. I rewrote the test to assert both defences, and added the opposite case (`'…/guide #setup'` **is** a hashtag) so the URL stripping cannot silently become too greedy.
  - Two smaller AI-introduced compile errors, both found by `tsc`: `assert.throws()` is typed as returning `void`, so the thrown error has to be captured with try/catch, and `node --test dist/` treats the path as a file, so the script needs the glob `"dist/**/*.test.js"`.
  - Length is counted in Unicode code points, not `String.length`. `"ab😀".length` is 4 because the emoji is two UTF-16 units, which would mis-measure a 280-character tweet. The same trap exists in C# with `string.Length`.
- **2026-10-19: EVIDENCE.md started.** Proofs recorded per step, while the transcripts are fresh, so nothing has to be reproduced at submission time. The ingestion proofs were re-captured with `curl` rather than reusing my PowerShell output, so the command printed next to each transcript is literally the one that produced it.
  - The requirement table marks what is **not** done yet instead of leaving rows blank, and E2c says plainly that it shows a shape rather than a captured response, because no endpoint returns it yet.
- **2026-10-19: variant endpoints.** `POST /posts/:id/generate`, `POST /posts/:id/variants`, `GET /posts/:id/variants`, `GET /variants/:id`, plus 13 generator tests. `npm test` passes 32/32. **Phase 2 gate met**: one post produces three different valid variants, and a rule-breaking variant is refused with the rule named.
  - Shaping and validation are deliberately separate. The template shapes text (truncate to fit, top N tags, normalise tone) and is allowed to be imperfect; `assertValidVariant` is the gate that decides what may be stored. Generated and hand-written variants go through the same gate, so a template bug cannot sneak a bad variant into review.
  - Generation is **all or nothing**, inside one transaction. If any platform's text fails validation, nothing is stored and the error names the platform and the rule. Half a campaign is worse than none.
  - **Bug I found by reading the output, not from a failing test:** every variant repeated the title twice. My sentence splitter split on `.!?`, but a Markdown heading has no full stop, so the heading glued itself to the next sentence and my title-dedupe filter never matched the merged string. Fixed by dropping the leading heading line and splitting into paragraphs before sentences. Now covered by a regression test that counts occurrences of the title.
  - **Second bug, same step, caught by reading a transcript carefully:** after regenerating, post 1 had *two* `x` variants. `findByPostAndPlatform` used `ORDER BY id DESC LIMIT 1`, so it only ever saw the newest draft for a platform, deleted that one, and orphaned the older one. Repeated regeneration would have piled up duplicates. Replaced with `listReplaceable` (all `draft`/`rejected` rows) and `findDecidedByPostAndPlatform` (any `approved`/`published` row, which is never touched). Verified live: regenerating twice holds at exactly one variant per platform.
  - Lesson for the rest of the project: both of these passed the build and the tests I had written. Only reading the actual output caught them. I will keep inspecting transcripts rather than trusting green builds, which matters more once the worker is publishing for real.
  - Tone shaping changes the author's words, which deserves stating: `ALWAYS` becomes `Always`, `!!!` becomes `!`, and forbidden slang is dropped. Nothing is reworded and no claim is added or removed. Without it, a shouty blog post could not be published to X at all, for a reason the user cannot act on.
  - Polish: error messages now say "1 exclamation mark" rather than "1 exclamation marks". These strings end up in EVIDENCE.md and in front of a reviewer.
- **2026-10-19: shaping made visible.** Each variant now stores `shaping_notes` and returns them from generate and every variant read. Rationale written into `docs/DESIGN.md`.
  - My requirement, not the AI's suggestion: shaping rewrites the author's words (de-shouts, drops slang, cuts length), and a reviewer approving the final text makes that safe but not transparent. The notes say which rule caused each change, which a plain diff against the source would not.
  - Needed a schema change on a table that already existed, so `CREATE TABLE IF NOT EXISTS` was not enough. Added a tiny `migrate()` with an `ensureColumn` check in `src/db/index.ts`, a deliberately small stand-in for EF Core migrations. Verified by booting against the database created before the column existed: it logged `[db] added column variants.shaping_notes` and the old rows read back with empty notes.
  - **A behaviour bug the notes themselves exposed.** With notes switched on, Discord reported "removed 2 exclamation marks" even though its profile permits three. The collapse of `!!!` to `!` ran unconditionally, so shaping was rewriting text that would have passed. Fixed so shaping only acts when a profile is actually breached. Making the behaviour visible is what revealed it, which is an argument for the feature beyond honesty.
  - Two test failures worth keeping: a note saying "used 0 of 1 tags" for Discord was noise (a profile that allows no hashtags is the platform's nature, not something shaping did), and my truncation test used many short sentences, which the X template never truncates because it takes only the first one.

## Phase 3: Review workflow

- **2026-10-19: approve, reject, edit.** `POST /variants/:id/approve`, `POST /variants/:id/reject`, `PATCH /variants/:id`, plus the transition table in `src/variants/workflow.ts` and 10 tests. `npm test` passes 48/48.
  - The transitions are **one table**, not if/else spread across routes. Reading that table is how you check the rules, and adding a transition is one edit. A test iterates every status to prove nothing can leave `published` and nothing can declare itself `published`.
  - Approving an already-approved variant returns **409, not 200**. Silently accepting a no-op would let a caller believe it changed something.
  - Editing sends a variant back to `draft` and clears its shaping notes. An approval attached to different words means nothing, and after a human edit the words are no longer the generator's.
  - Status changes are a compare-and-set (`UPDATE ... WHERE id = ? AND status = ?`). If two reviewers act at once the loser gets 409 instead of overwriting the winner. Same idea as a `rowversion` check in EF Core, done by hand.
  - Not graded but it mattered: the AI's first refusal message read "Variant is already approved, not approved", because the service appended the target status to a message that was already complete. `explainRefusal` now returns the whole sentence and the caller never appends. There is a test asserting the string does not contain "not approved".
  - **Process note, my mistake not the code's.** My first live transcript looked right but its starting state was wrong: an earlier run had failed in my shell helper *after* the curl calls had already changed the data, so the "editing clears the shaping notes" step started from a variant that had none. I rebuilt the transcript from a genuinely fresh database. Worth recording because the evidence file is only as good as the state it was captured in.

## Phase 4: Adapters and idempotent publish

- **2026-10-19: SocialPublisher interface and the two mocks.** `src/publishers/{types,mock,index}.ts`, the `/mock/posts/:id` preview, and 9 mock tests. `npm test` passes 57/57.
  - The interface carries two members the first design doc did not have, both earning their place:
    - `dedupesByKey`, the flag the entire crash-safety argument turns on. After an **ambiguous** failure the worker may retry only an adapter that returns `true`. A Discord webhook returns `false`, so it is parked instead. Putting this on the adapter means the retry decision is made from what the protocol actually guarantees, not from a guess in the worker.
    - `deduplicated` on a success, so the history can tell a fresh post from a retry the target absorbed.
  - Failures are classified **by the adapter** (`retryable` / `permanent` / `ambiguous`), because only the adapter knows its protocol. Misclassifying `ambiguous` as `retryable` is precisely how duplicates happen, so the type makes the choice explicit rather than letting a `catch` block decide.
  - Mock dedupe is enforced by `UNIQUE (adapter, idempotency_key)` in the schema, using `INSERT ... ON CONFLICT DO NOTHING RETURNING id`. One statement distinguishes a fresh insert (a row comes back) from a repeat (nothing comes back), so there is no read-then-write race. Not a check in application code, which could be wrong under concurrency.
  - A test I wrote deliberately: same key, **different text**, keeps the first text. The key identifies the intended post, so once it is sent the text is settled. A retry must not quietly rewrite a message that is already live.
  - Mock tests run `openDatabase(':memory:')`, so they exercise the real schema and the real constraint, not a stub.
  - `createPublisher` is the only code that maps a name to an implementation. Verified by grep: nothing outside `src/publishers/` names a concrete adapter. That grep is the probe 6 proof, recorded in EVIDENCE.
  - Design decision recorded in `docs/DESIGN.md` before writing the worker: the crash window gets an injectable `afterSend` hook (unused in production) so a test can fail exactly between the send and the result write, plus a real kill-the-worker transcript. My requirement, because a reviewer can rerun a test but can only read a transcript.
- **2026-10-19: the real Discord adapter.** `src/publishers/discord.ts`, `src/redact.ts`, 25 adapter tests and 7 redaction tests. `npm test` passes 89/89.
  - Failure classification was specified by me before coding, because this is where the dedupe argument holds or quietly breaks. The asymmetry: a wrong `retryable` posts the message twice, a wrong `ambiguous` costs one manual resolution. So anything that might already have been processed is `ambiguous`. The full table with reasoning is in `docs/DESIGN.md`, and every row has a test.
  - The one I would have got wrong by instinct: **5xx is ambiguous, not retryable.** A 5xx is not proof of non-delivery, because Discord can accept and process a message and then fail on the way back, in a gateway or load balancer. Treating 5xx as retryable is the classic duplicate-post bug.
  - A case I had not considered until writing the tests: **2xx with an unreadable body must count as success.** Discord accepted the message, so reporting a failure would cause a retry and the duplicate it appears to be preventing. The attempt is recorded as succeeded with id `unknown`, and the reason is in a comment at the code.
  - `?wait=true` costs one round trip and buys the message id and link, plus the smallest possible crash window, because the outcome is known as early as it can be.
  - `allowed_mentions: {parse: []}` on every request, as a second line of defence behind the `no_mass_mentions` rule. Even a variant that somehow contained `@everyone` could not ping the server.
  - **A real hole the secret audit found, not a theoretical one.** I checked every path the webhook URL could escape through rather than only the adapter, and `src/http/errors.ts` logged any unhandled error in full. Nothing reaches it today, because the adapter returns failures rather than throwing, but an error carrying the URL thrown from any future code path would be written straight to the log. Redaction is now centralised in `src/redact.ts` and applied at all three places that print arbitrary text: the Express error handler, the boot failure and the adapter warning.
  - Redaction matches the **shape** of a webhook URL rather than comparing against the configured value, so a URL from a redirect, a nested `cause` or a copy of the config is caught too. `fetch` in particular throws a bland "fetch failed" and hides the real error, URL included, in `cause`, which `redactError` unwraps and then redacts.
  - Tests inject a `fetch` stub, so all 25 adapter cases run with no network and no real webhook. The leak test drives all eight failure paths with a realistically-shaped fake URL and asserts the URL, the token and the numeric webhook id are absent from every string that would be stored.
  - Honest correction while writing EVIDENCE: I recorded "no route mentions the webhook" and then my own new explanatory comment in `errors.ts` made that grep match. The evidence now shows the real output and says the single match is a comment.
- **2026-10-19: process-level crash handlers.** `src/process-guards.ts`, wired in `main.ts` before anything else runs, with 5 tests.
  - **My gap, and the AI had missed it too.** Everything built so far redacts text that *the application* prints. Node prints two things itself, straight to stderr, before application code sees them: an unhandled promise rejection and an uncaught exception. Its default output includes the `cause`, which is exactly where `fetch` hides the request URL. So a rejected promise from a publish path would have printed the webhook URL despite the Express handler, the adapter redaction and the boot-failure redaction.
  - Both handlers report and then **exit non-zero**. After an uncaught exception the process state is undefined, so continuing to serve requests would be worse than stopping.
  - The tests run in **real child processes**, because installing the handler is precisely what suppresses Node's default output. Nothing in-process could demonstrate the behaviour.
  - The test I am most pleased with is the **control case**: a child with no handlers installed, asserted to leak the URL. It proves the handler is what prevents the leak, rather than the leak being impossible anyway. Without it the other four assertions could pass vacuously and I would never know.
- **2026-10-19: job store and scheduling.** `src/jobs/{slots,repository,service}.ts`, `src/http/routes/jobs.ts`, 24 tests. `npm test` passes 118/118. **Phase 3 gate now met**: an unapproved variant cannot be scheduled, an approved one can.
  - The idempotency key is `variant:{id}:slot:{slot}` with the slot truncated to the whole minute in UTC. That truncation is what makes the key stable: `15:00:00Z`, `15:00:45Z` and `17:00:00+02:00` are one slot, so three ways of saying "the 15:00 post" cannot create three jobs. Verified live.
  - Uniqueness is decided by the `UNIQUE` index, not by a `SELECT` before the `INSERT`. Two simultaneous requests cannot both pass a check and insert; the loser catches the constraint violation and reads the winner's row. A check-then-insert would be a race, and this is the one place where a race means a duplicate post.
  - `POST /variants/:id/schedule` returns **201** for a new job and **200** for one that already existed. The same request twice is not an error: it is the same intent and yields the same single job.
  - The claim is one `UPDATE ... WHERE status = 'pending' ... RETURNING *`. SQLite serialises writers, so of two workers racing exactly one matches. A test claims the same job from two worker ids and asserts the second gets nothing.
  - A decision worth stating: **`attempts` increments at the claim, not after the send.** A job that crashes mid-publish has still used an attempt, so a crash loop cannot retry for ever. Incrementing after the send would let a repeatedly-crashing job retry indefinitely.
  - `settle` is guarded on `status = 'claimed'`, so a worker whose lease expired cannot overwrite the outcome recorded by whoever took the job over. There is a test for exactly that.
  - Added `+2m` as an accepted value for `at`. Probe 4 asks for "two minutes out" specifically, and hand-writing an ISO timestamp for that invites mistakes.
  - Editing an approved variant now cancels its pending jobs, as the design doc said it should. Otherwise a job would publish words that are no longer approved, possibly the exact words the editor was removing. The server logs how many it cancelled.
  - `POST /jobs/:id/resolve` is the human decision for a job parked as `unknown`. It only applies to a parked job, and a `succeeded` resolution also marks the variant published, because the message is live even though this process never saw the confirmation.
